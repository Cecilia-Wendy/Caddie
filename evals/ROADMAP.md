# Caddie 质量评测中心开发计划

状态：**已规划，暂不进入普通用户主流程**
计划类型：内部开发与发布前质量保障
底层能力：第一版本地 eval harness 已完成，位于当前目录。

## 产品定位

质量评测中心是 Caddie 的内部“质量体检中心”，用于在提示词、模型、检索、上下文装配或 Agent 流程变化后判断：

- 是否开始编造经历、数字或个人贡献；
- 是否遗漏用户材料中的重要事实；
- 内容是否真正针对目标岗位；
- 信息不足时是否主动提示补充或确认；
- 新版本相对旧版本是提升还是退步；
- 不同模型在质量、稳定性、耗时和成本上的差异。

## 当前已完成

- 本地、可重复运行的 eval runner；
- 事实忠实度、数字依据、事实覆盖、岗位相关性、信息边界和套话检查；
- 简历改写、贡献边界、JD 定制、公司研究四类匿名核心案例；
- JSON 报告输出与回归失败退出码；
- 自动化反例测试，可拦截典型编造和夸大；
- 不读取真实用户数据库的离线 smoke 模式。

## 近期使用方式

完整 UI 建设前，在以下时机由开发流程运行：

1. 更换默认模型或调整模型能力档案；
2. 修改核心提示词、上下文装配和检索逻辑；
3. 修改事实写入、用户确认或 Agent 执行边界；
4. Alpha/Beta 发布前；
5. 用户指出编造、遗漏或严重偏题后，将匿名化失败案例加入回归集。

```bash
.venv/bin/python -m evals.runner --live --output output/eval-report.json
```

## UI 入口规划

未来入口建议放在：

> 设置 → 开发者工具 → 质量评测

不进入普通用户主导航。最小 UI 包含：

- “运行核心评测”按钮；
- 本次通过率、平均分、耗时和使用模型；
- 各案例通过/失败状态及具体失败项；
- 与上一次结果的对比；
- 导出完整 JSON 报告。

## 启动 UI 开发的条件

- 匿名真实案例达到 20～30 个；
- 覆盖简历、项目表达、面试回答、岗位研究和多轮 Agent 任务；
- 出现实际的模型切换或提示词版本比较需求；
- 评分规则经过一轮人工抽检和校准；
- 明确报告保存位置、隐私边界和历史版本保留策略。

## 后续阶段

### Phase 1：扩充真实回归集

- 将用户拒绝、重度修改和纠正编造的案例匿名化；
- 为每个失败案例记录问题类型和修复版本；
- 建立 capability eval 与 regression eval 两组案例。

### Phase 2：模型与版本对比

- 同一批案例运行多个模型或提示词版本；
- 同时报告质量、耗时、token 和失败稳定性；
- 支持多次 trial，避免把单次随机结果当成结论。

### Phase 3：内部质量评测 UI

- 增加开发者工具入口；
- 展示历史趋势和版本差异；
- 发布前可选择将核心回归失败作为阻断条件。

## 产品原则

- Eval 用于支持开发决策，不用于制造好看的单一分数；
- 公共 benchmark 不能替代 Caddie 自己的真实求职任务；
- 硬事实和安全边界优先于文风评分；
- 自动评分不能完全替代人工审阅；
- 案例必须匿名化，不保存个人联系方式、原始简历全文和未公开公司资料。
